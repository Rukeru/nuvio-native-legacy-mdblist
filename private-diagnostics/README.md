# Private TV diagnostics

This deploys to the existing `nuvio-diagnostics-api` Worker and
`nuvio-diagnostics` D1 database, binding `DB`. It does not create either resource.
Reports can be read or deleted only through your authenticated Cloudflare D1
console. The Worker has no administrative HTTP endpoints. Application uploads
must remain disabled until deployment, pairing and the smoke checks below pass.

## What is accepted

`POST /v1/diagnostics` accepts version 1 JSON, at most 64 KiB and 32 events.
`ingestion.mjs` is the protocol allowlist: known event codes and bounded integer
measurements only. Messages, severity and category are generated by the server.
No free-text logs, titles, viewing history, URLs, account IDs, session tokens,
provider keys or authorization headers are stored in reports. Unknown fields
are rejected, including nested ones. Credentials authenticate the transport;
only their SHA-256 hashes are stored separately from reports.

Each installation has its own random 256-bit upload token. A ten-minute,
128-bit one-use enrollment code, provisioned through the authenticated D1
console, authorizes pairing. There is no anonymous persistent registration,
global application secret or public report-reading permission. A lost pairing
response may be retried only with the same token. A used code cannot undo
revocation or a later credential rotation. TLS is mandatory; do not disable
certificate verification on the TV.

## Deploy using your existing resources

1. Install Node.js 24 from the official Node website. Open a terminal in this
   repository's `private-diagnostics` directory and run `npm ci --ignore-scripts`.
2. Run `npm test` and `npm run check`. These use temporary local databases and
   a dry-run bundle; neither command deploys to Cloudflare.
3. Run `npx wrangler login`. Complete Cloudflare's browser login yourself.
   Never paste a Cloudflare API token, password, or login code into chat.
4. In Cloudflare, open **Storage & databases → D1 → nuvio-diagnostics**.
   Copy its **Database ID** (an identifier, not a secret). Copy `wrangler.jsonc`
   to `wrangler.local.jsonc` and replace `REPLACE_WITH_EXISTING_DATABASE_ID`
   in that local file. Keep the Worker name, database name and `DB` binding.
   Confirm the two numeric rate-limit namespaces are unused by other Workers
   in your account; choose two unique positive numbers if necessary.
5. Check the existing Worker using
   `npx wrangler deployments list --config wrangler.local.jsonc` and the
   database using `npx wrangler d1 info nuvio-diagnostics --config wrangler.local.jsonc`.
   Stop if either is missing or belongs to the wrong account. Do not run a
   `create` command. Retain the previous Worker deployment for rollback.
6. Apply the schema to that existing database:
   `npx wrangler d1 migrations apply nuvio-diagnostics --remote --config wrangler.local.jsonc`.
   Use the migration command rather than pasting the whole file into D1's
   line-oriented `exec` API; the migration includes multi-line triggers.
7. Deploy with uploads disabled:
   `npx wrangler deploy --config wrangler.local.jsonc`.
   Open `https://nuvio-diagnostics-api.rukeru23.workers.dev/healthz` and confirm
   `{"version":1,"ready":false}`. Confirm the D1 `DB` binding still points to
   your existing database and the daily Cron is `17 3 * * *` (UTC).
8. After the local security tests and bindings are verified, set only
   `INGESTION_ENABLED` to `"true"` in the local config and deploy again.
   `/healthz` should return `ready:true`. An unauthenticated POST with JSON
   to `/v1/diagnostics` must return 401. GET/DELETE on that path must return
   405; `/v1/reports` must return 404. No personal diagnostic data is involved.
9. Pair a test installation, send the allowlisted manual report, and check
   its receipt in D1. Revoke its token and verify another upload returns 401.
   Only after these live checks pass should production TV uploads be enabled.
   A successful local test is not proof of a successful remote deployment.

Wrangler 4.149.0 and all development dependencies are pinned in `package-lock.json`.
The Worker itself has no runtime npm dependencies. Worker request/body logging
is disabled and the implementation never prints request bodies, headers or
database exceptions. Keep that policy when adding diagnostics.

## Pair Samsung and LG separately

In the `private-diagnostics` terminal run `node tools/enrollment.mjs tizen` for Samsung,
or `node tools/enrollment.mjs webos` for LG. The helper prints two local file
paths, not credentials. Open the SQL file and execute that single INSERT in
the authenticated D1 console. Open the JSON file locally and enter its
32-character pairing code in the TV's private-diagnostics pairing field within
ten minutes. The TV generates and stores its own upload secret; the pairing
code is not an MDBList, Nuvio, Trakt or Cloudflare credential.

The `.private` directory is git-ignored. Keep it private and delete expired
pairing files through your file manager. On Windows, keep these files under
your user account; POSIX file modes do not replace Windows account permissions.
Never put these files in a GitHub issue, release, screenshot or chat.

To revoke a TV, use the installation lookup and UPDATE in `queries.sql`.
To rotate, run `node tools/enrollment.mjs tizen EXISTING_INSTALLATION_UUID`
(or `webos`), apply its new SQL, then pair that TV again. The new token
immediately replaces the old one without changing the installation's report
ownership. Revocation does not delete reports; retention still applies.

## Limits, retention and failures

The database enforces 20 installations, 20 reports per installation per rolling
24 hours, 100 reports globally per rolling 24 hours, and 1,500 stored reports.
These limits are transactional, including concurrent requests. Idempotent
duplicate delivery does not add a row or consume that quota. The same report ID
with changed data returns 409. A receipt collision is retried at most three times.
Daily Cron deletes reports older than 14 days and expired enrollment codes.
Expired reports can remain until the next daily cleanup, at most about 24 hours
longer; the 1,500-record limit protects storage if Cron stops working.

Additional edge limits are five pairing attempts per minute per IP and thirty
upload attempts per minute per IP and authenticated installation. Shared home
IPs can share the coarse limit. Cloudflare's edge limits are per location and
eventually consistent; they are abuse protection, not the global storage quota.
See [Cloudflare rate limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/).

At the 64-KiB input ceiling, 1,500 reports are under 94 MiB of payload before
indexes/database overhead; actual allowlisted reports are much smaller. D1 Free
currently allows 5 million rows read/day, 100,000 written/day, 5 GB total account
storage, with a 500 MB limit per database. Index maintenance also counts toward
writes. Workers Free also has request/CPU limits. Abuse or another application
sharing the account can exhaust a free quota despite these caps; ingestion then
fails safely and TVs keep bounded local queued data. Do not silently enable a
paid plan. See [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/)
and [D1 limits](https://developers.cloudflare.com/d1/platform/limits/).

400/409 are permanent payload errors; 401 requires pairing or credential repair;
429 uses Retry-After; network errors and 503 receive bounded client backoff.
There is no fallback to the upstream developer's reporting service.
Use `queries.sql` for private viewing, receipt lookup and individual deletion.

## Validation and release boundaries

The focused suite checks privacy rejection, both platforms, authentication,
expiration, rotation, revocation, idempotency, concurrency, rollback, quotas,
retention, bounded storage and safe error responses using real SQLite. A
separate test runs the actual Worker and D1 migration in Cloudflare's workerd
runtime through Miniflare. Dry-run validation checks the deployable bundle.
Backend-only changes select this short gate, not complete TV builds. Both TV
publication workflows require the backend gate in addition to their native
package and complete regression evidence. No tests deploy automatically.
